# 믹스 입력 베이스 전용 소형 모델 계획

작성 2026-10-25. 원본은 Claude Docs 문서 [믹스 입력 베이스 전용 소형 모델 계획](https://claude.ai/artifact/49vfMMLDK8sbHvwXVRW81g)이고, 이 파일은 오버나이트 작업용 사본이다. 둘이 다르면 사용자에게 어느 쪽이 최신인지 묻는다.
상태: **계획 확정, 실행 전.** 1주차 작업부터 시작한다. 판정 규칙(평가 계획 절)은 학습 시작 전에 고정한 것이며, 바꾸려면 날짜와 이유를 이 파일에 적는다.
함께 읽기: `eval/BEST_RESULTS.md`(2절 베이스), `eval/ROUND2_REPORT.md`, `eval/OVERNIGHT_REPORT.md`, `../reports/Trackform 앞으로의 방향.md`(원칙 1~7).

## 요약

전체 곡 믹스를 받아 베이스 노트만 내는 3M 파라미터 안팎의 전용 모델을 만든다. 목표는 YourMT3+ 믹스 입력의 이득(실베이스 +0.17~+0.19)을 데스크톱 앱에 넣을 수 있는 크기(수 MB)로 가져오면서, YourMT3+가 약한 옥타브 정확도(업라이트 엄격 F1 0.305 vs 현행 0.444)는 지키는 것이다.

- **핵심 가설:** 베이스는 저음 단선율이라 거대 다악기 모델이 필요 없다. 학습 데이터의 음색이 실제와 맞으면 작은 모델로 충분하다.
- **가장 큰 위험:** 렌더링 데이터로만 학습하면 실제 녹음에서 무너진다(R4 드럼 파인튜닝 −0.043). 그래서 실제 연주 평가셋을 학습보다 먼저 만들고, 실제 DI 베이스를 학습 데이터에 넣는다.
- **성공 기준:** 실제 연주 테스트셋과 실베이스 두 세트에서 현행 하이브리드 대비 paired 95% CI 하한 > 0, 그리고 엄격 F1이 현행보다 낮지 않을 것.
- **기간:** 5~6주. 1주차 끝과 3주차 끝에 중단 판정이 있다.

## 배경과 근거

믹스 입력 YourMT3+는 세 세트 모두에서 현행을 유의하게 앞섰지만, 같은 모델에 스템을 넣으면 실베이스에서 최하위였다. 이득의 원천은 모델 크기가 아니라 '반주의 화성·리듬 맥락'과 '분리 아티팩트가 없는 입력'으로 보인다. 작은 모델도 가질 수 있는 성질이다.

출처: `eval/BEST_RESULTS.md` 2절. Slakh test 20곡, pitch-class onset F1(50 ms), 곡별 평균, 괄호는 현행 대비 paired 95% CI.

| 시스템 | 신스 Slakh | 실베이스 일렉 | 실베이스 업라이트 | 업라이트 엄격 F1 |
| --- | --- | --- | --- | --- |
| 현행 (htdemucs 스템 → Basic Pitch + 하이브리드) | 0.582 | 0.287 | 0.480 | 0.444 |
| YourMT3+ 스템 입력 | 0.733 (+0.151) | 0.101 (−0.186) | 0.239 (−0.241) | 0.142 |
| **YourMT3+ 믹스 입력** | **0.852 (+0.270)** | **0.479 (+0.192 [+0.075, +0.320])** | **0.653 (+0.173 [+0.062, +0.293])** | 0.305 |
| 노트 시작 보정 (후처리) | +0.100 | +0.017 [−0.001, +0.044] | +0.014 [+0.001, +0.028] | — |

이 계획이 받아들이는 교훈은 네 가지다.

1. **신스 렌더로 모델을 고르면 순위가 뒤집힌다(R1).** 검증·선택은 실제 음색 세트로만 한다.
2. **렌더링만으로 학습하면 실제에서 잊는다(R4).** 실제 녹음 데이터가 학습에 들어가야 한다.
3. **실베이스 손실의 주원인은 노트 시작 타이밍이다.** 짧은 스타카토(정답 중앙 0.2초)와 느린 피치 성장(기본음이 100~160 ms에 나타남) 때문에 50 ms 허용오차를 놓친다. 모델에 어택 전용 온셋 헤드가 필요하다.
4. **Lakh MIDI로 학습하면 Slakh 계열 테스트가 오염된다(MuScriptor N1).** 학습 MIDI에서 테스트 곡을 빼는 것이 필수다.

## 학습 데이터

학습 데이터는 세 층으로 쌓는다. 렌더링 데이터(A)로 기초를 만들고, 실제 DI 베이스(B)로 실제 음색을 가르친다. YourMT3+ 의사 라벨(C)은 B가 부족할 때만 쓴다. 규모는 정해 두지 않고, 1주차에 잰 처리량으로 정한다.

| 층 | 원천 | 만드는 법 | 역할 | 상태 |
| --- | --- | --- | --- | --- |
| **A. 일관 렌더** | Lakh MIDI(clean) 중 베이스 트랙이 있는 곡. Slakh train 원본 MIDI 포함 | 베이스는 `build_realbass.py` 방식으로 **학습 전용** 실제 베이스 단음 샘플로 렌더. 반주는 같은 MIDI를 사운드폰트로 렌더 | 화성·리듬 맥락이 맞는 대량 데이터. 정답이 정확하다 | 렌더러 있음. 로컬 Slakh train은 53곡뿐 |
| **B. 실제 DI 베이스** | 공개 멀티트랙(Cambridge-MT Mixing Secrets, MedleyDB) 중 베이스 DI 트랙이 있는 곡 | 깨끗한 DI에서 자동 라벨(현행 하이브리드 + pYIN + 온셋). 입력은 원래 실제 믹스 | 실제 연주·실제 음색·실제 믹스. R4의 망각을 막는 층 | 라이선스·수량 확인 필요 |
| C. 의사 라벨 (선택) | 라벨 없는 실제 음원 | YourMT3+ 믹스 출력에서 현행 하이브리드와 일치하는 노트만 남김 | 음색 다양성 보충 | B가 50곡 미만일 때만 |

### B층이 이 계획의 핵심이다

멀티트랙의 베이스 DI는 반주 없는 단선율이다. 믹스에서 베이스를 찾는 것보다 훨씬 쉬운 문제라, 이미 가진 도구로 높은 정확도의 라벨을 만들 수 있다. 그러면 '실제 믹스 → 거의 정확한 베이스 MIDI' 쌍이 녹음 없이 생긴다.

- 자동 라벨의 정확도는 사람이 고친 부분집합으로 잰다. DI 라벨 onset F1이 0.95 미만이면 B층은 학습에 바로 쓰지 않고 수작업 교정 분량을 늘린다.
- 같은 원천에서 테스트셋(T1, 아래 절)도 만든다. 곡 단위로 나누고, 같은 아티스트·같은 세션은 한쪽에만 둔다.
- 라이선스는 연구용 기준으로 기록만 하고(`eval/LICENSES.md`), 오디오는 재배포하지 않는다. Cambridge-MT의 사용 조건과 MedleyDB 신청 절차는 1주차에 확인한다.

### 샘플 라이브러리 분리 (오염 방지 1)

테스트 세트에 쓴 음색은 학습에 절대 넣지 않는다. 넣으면 실베이스 점수가 음색 암기를 재게 된다.

| 용도 | 라이브러리 |
| --- | --- |
| 테스트 전용 | Karoryfer Fashionbass(일렉), D. Smolken 업라이트 |
| 개발 전용 | Black-and-Blue(일렉, 인덱스 −12 보정 적용) |
| 학습 | 위 세 개를 뺀 CC0·CC BY 멀티샘플 베이스. 일렉 4종 이상, 업라이트 2종 이상을 1주차에 수집. 모자라면 B층의 실제 DI로 음색 다양성을 채운다 |

### 곡 분리 (오염 방지 2)

- Slakh test 20곡과 dev_realbass 30곡의 원본 Lakh MIDI를 A층에서 뺀다. Slakh `metadata.yaml`의 Lakh UUID로 매칭하고, UUID가 없으면 베이스 노트 시퀀스 해시로 매칭한다.
- Lakh에는 같은 곡의 다른 편곡 MIDI가 여럿 있다. 제목·아티스트 메타데이터가 같은 파일도 함께 뺀다.
- 제외 목록은 `eval/bass_model/exclude.json`에 고정하고, 학습 스크립트가 시작할 때 검사한다.

### 증강 (학습 중 즉석 합성)

베이스 스템과 반주를 따로 저장하고 학습 중에 섞는다. 같은 곡이 매번 다른 조건으로 나오게 하기 위해서다.

- 베이스 대 반주 레벨 −12~+6 dB, 베이스 EQ·컴프레서·앰프 시뮬레이션(pedalboard), 리버브
- 전체 믹스에 리미터, AAC/MP3 코덱, 휴대폰 대역 제한(공연 녹음 대비)
- 피치 시프트는 하지 않는다. 저음 음색이 바뀌고 옥타브 판단을 흐린다. 음역 다양성은 MIDI 자체에서 얻는다

### 저장

로컬 디스크 여유가 24 GB다. 학습 데이터는 외장 SSD에 16 kHz 모노 FLAC으로 둔다(100시간 기준 약 6 GB). 경로는 환경변수로 넘기고, 원본은 `data/raw/`, 가공본은 `data/processed/`에 둔다.

## 모델 구조와 크기

기본안은 3M 파라미터의 CRNN(합성곱 + 컨포머)이다. 단선율 전제를 구조에 넣어, 다악기 모델이 배우는 데 쓰는 용량을 아낀다. 크기는 세 가지를 학습해 개발셋에서 고른다.

### 입력

- 16 kHz 모노 믹스, 10 ms 홉, 10초 창(추론은 1초 겹침)
- **피치 가지:** HCQT(배음 0.5·1·2·3·4·5), A0(27.5 Hz)부터 반음당 3빈. 기본음이 약한 저음에서도 배음으로 피치를 잡는다. Basic Pitch와 같은 방식이다
- **어택 가지:** 로그 멜 128빈(8 kHz까지). 피치가 100~160 ms 뒤에야 서는 음색에서도 픽의 광대역 과도음으로 시작 시각을 잡기 위한 가지다(배경 교훈 3)

### 구조

1. 피치 가지: 배음 채널 위 2D 합성곱 4층 → 프레임마다 피치별 임베딩
2. 어택 가지: 2D 합성곱 3층 → 주파수 축 풀링
3. 두 가지를 잇고 시간 축 컨포머(또는 BiGRU)로 수 초 맥락을 본다. 반주의 화성·박자 맥락이 여기서 들어온다
4. 출력 헤드 네 개
    - **단선율 피치:** 프레임마다 46클래스 소프트맥스(B0~G#4 45음 + 무음). 한 번에 한 옥타브만 고르게 해 옥타브 오류를 구조적으로 줄인다
    - **온셋:** 프레임별 이진, 정답은 ±20 ms 가우시안으로 부드럽게
    - **오프셋:** 프레임별 이진
    - **벨로시티:** 온셋 프레임에서 회귀. YourMT3+는 상수를 내므로 여기서도 이길 여지가 있다
5. 디코딩: 온셋에서만 피치 전이를 크게 허용하는 비터비. 물리 규칙(모노포니, 재타격 불응기)만 남기고, 기존 후처리 체인은 붙이지 않는다(원칙 3)

### 크기 후보

| 크기 | 시간 축 | 파라미터 | 예상 파일(fp16) | 역할 |
| --- | --- | --- | --- | --- |
| S | BiGRU 2층, 96 | 약 0.5M | 1 MB | 하한선. 가장 빠르다 |
| **M (기본안)** | 컨포머 4층, d=192 | 약 3M | 6 MB | 주 후보 |
| L | 컨포머 6층, d=256 | 약 10M | 20 MB | 용량이 병목인지 확인용 |

선택 규칙: 개발셋 최고 점수와 0.01 안에 드는 가장 작은 크기를 고른다. L이 M보다 0.03 넘게 앞서면 데이터보다 용량이 병목이라는 뜻이니 한 단계 더 키워 본다.

### 학습과 연산

- 손실: 피치 교차 엔트로피 + 온셋·오프셋 BCE(양성 가중) + 벨로시티 MSE(온셋 프레임만). AdamW, 배치 16
- 장비: M1 Max 32 GB(MPS). 조건당 12시간 안에 끝나는 것을 목표로 한다. 1주차에 M 크기 처리량(초당 오디오 시간)을 재고, 12시간을 넘기면 클라우드 GPU 임대를 검토한다
- 추론 목표: 1분짜리 곡을 CPU에서 6초 안에. ONNX로 내보내 데스크톱 사이드카에 넣을 수 있어야 한다. YourMT3+는 크기 때문에 DMG에 넣지 못했다

### 사전 등록 절제 (개발셋에서만)

| 질문 | 비교 |
| --- | --- |
| 믹스가 정말 나은가 | 믹스 입력 vs htdemucs 스템 입력(같은 모델·같은 데이터) |
| 단선율 헤드가 도움이 되는가 | 46클래스 소프트맥스 vs 피치별 시그모이드(Onsets and Frames 방식) |

## 평가 계획

대표 테스트는 새로 만드는 실제 연주 베이스셋(T1)이다. 기존 실베이스 두 세트는 함께 통과해야 하는 조건이고, 신스 Slakh는 참고값이다. 하니스는 지금과 같다: 채점 v2, 곡별 평균, paired 95% 부트스트랩 CI 10,000회(seed 0).

### 세트

| 세트 | 내용 | 역할 | 학습과의 분리 |
| --- | --- | --- | --- |
| **T1 실제 연주** | 실제 멀티트랙 믹스 + 사람이 검수한 DI 베이스 MIDI, 15곡 이상(아래 절) | **대표** | B층과 곡·아티스트·세션 모두 분리 |
| T2 실베이스 일렉 | Slakh test 20곡, Fashionbass 재렌더 (`slakh_realbass`) | 필수 통과 | 테스트 MIDI·라이브러리 모두 학습에서 제외 |
| T3 실베이스 업라이트 | Slakh test 20곡, Smolken 재렌더 (`slakh_realbass_up`) | 필수 통과 | 같음 |
| T4 신스 Slakh | Slakh test 20곡 원 렌더 (`slakh`) | 참고 | 테스트 MIDI 제외 |
| 개발 | dev_realbass 30곡(Black-and-Blue) + B층에서 떼어 둔 검수 곡 5곡 | 크기·조건·문턱 선택 | 학습에서 제외 |

### 지표

- **대표:** pitch-class onset F1(50 ms). 기존 결과와 바로 비교하기 위해서다
- **필수 보조:** 엄격 F1(옥타브 포함). T1·T2·T3에는 옥타브 접힘이 없어 의미가 있다
- 보조: offset F1, 벨로시티 Spearman ρ(Slakh test 중 정답 벨로시티가 변하는 9곡), 1분당 처리 시간, 모델 파일 크기

### 사전 등록 판정 규칙

학습을 시작하기 전에 이 규칙을 고정하고, 바꾸려면 바꾼 날짜와 이유를 적는다.

1. **기본값 교체(전체 곡 → 베이스 경로):** 현행 대비 대표 지표의 CI 하한이 T1·T2·T3 모두에서 0보다 크다. 엄격 F1 차이의 CI 하한이 T1·T3에서 −0.02보다 크다. 피아노 회귀 sha256이 일치한다.
2. **연구 주장(YourMT3+ 수준):** T1에서 (새 모델 − YourMT3+ 믹스)의 CI 하한이 −0.03보다 크면 '동등'으로 쓴다. 결과와 상관없이 기록한다.
3. **테스트는 단계마다 1회.** T1은 최종 후보 하나만 채점한다. 크기·절제·문턱은 개발셋에서만 고른다.
4. **개발셋은 붕괴 탐지용이다.** 현행 하이브리드의 개발셋 점수(0.629)는 튜닝에 쓴 점수라, 비교는 out-of-sample 수치하고만 한다.
5. **문턱 최적화는 두 개만.** 온셋 문턱과 최소 길이, 개발셋에서 격자 탐색.

## 실제 연주 베이스 테스트셋 구축

T1은 학습보다 먼저, 1주차에 만든다. 공개 멀티트랙의 베이스 DI에서 초안을 만들고 사람이 고친다. 녹음 장비·연주자 없이 실제 연주·실제 믹스의 정답을 얻는 가장 싼 방법이다.

### 곡 고르기

- 15곡 이상, 곡마다 60초 구간(30~90초, 기존 세트와 같은 창)
- 장르와 악기를 섞는다: 록·펑크(핑거·픽·슬랩), 팝, 재즈(업라이트), 메탈·저음(5현 B0 포함)
- 아티스트·세션 단위로 T1, 개발 5곡, B층 학습에 나눈다. 한 아티스트의 곡은 한쪽에만 둔다

### 만드는 절차

1. **정렬 확인:** DI와 믹스의 저역 대역을 교차상관해 시차를 잰다. 5 ms를 넘으면 보정하고 기록한다. 앰프 마이크 트랙만 있는 곡은 쓰지 않는다.
2. **초안:** DI에 현행 베이스 모드(하이브리드) + pYIN을 돌린다.
3. **교정:** Trackform 피아노롤에서 DI를 들으며 고친다. 고친 노트·걸린 시간을 로그로 남긴다. 이 로그는 그대로 '사용자 수정 로그' 데이터가 된다.
4. **검수:** 교정한 MIDI를 렌더해 DI와 겹쳐 들어 본다. 2곡은 일주일 뒤 처음부터 다시 라벨링해 두 번의 라벨 사이 onset F1을 잰다. 이 값이 점수의 상한이다.
5. **동결:** sha256과 매니페스트를 `eval/heldout/data/real_bass/`에 고정한다. 동결 뒤에는 라벨을 고치지 않는다(고칠 때는 버전을 올리고 모든 시스템을 다시 채점).

### 라벨 지침 (교정 전에 고정)

| 상황 | 처리 |
| --- | --- |
| 데드 노트·고스트 노트(음정 없음) | 라벨에서 빼고 별도 목록에 적는다. 채점 때 무시 구간 |
| 슬라이드 | 시작 음정의 노트 하나 + 벤드 표시. 도착음을 다시 치지 않았으면 새 노트가 아니다 |
| 해머온·풀오프 | 새 음정이 분명하면 새 노트 |
| 더블 스톱·코드 | 두 음 모두 라벨. 단선율 헤드가 놓치는 비율을 따로 보고한다 |
| 하모닉스 | 들리는 음정으로 라벨 |

### 비용

곡당 교정 시간은 모른다. 처음 2곡에서 재고, 곡당 45분을 넘으면 구간을 30초로 줄이고 곡 수를 유지한다. 곡 수가 길이보다 CI를 좁히는 데 더 중요하다. 교정은 베이스를 들을 수 있는 사람이 해야 하므로 사용자의 시간이 든다(총 15곡 × 45분 기준 약 11시간).

## 일정, 위험, 중단 규칙

6주 계획이고, 모델 학습은 2주차에야 시작한다. 실제 연주 테스트셋과 기준선이 먼저다. 세 번의 중단 판정은 모두 개발셋이나 기준선만 본다. 테스트셋은 6주차에 한 번만 연다.

| 단계 | 기간 | 할 일 |
| --- | --- | --- |
| 1. 준비와 기준선 | 1주차 | 데이터 접근 확인(Cambridge-MT·MedleyDB), 학습용 베이스 음색 수집, 제외 목록, M 크기 처리량 측정. T1 15곡 구축, 현행·YourMT3+ 기준선 채점 |
| **G1** | 1주차 끝 | T1 기준선에서 현행·YourMT3+가 모두 0.85 이상이면 문제가 작아 **중단**. DI 자동 라벨 onset F1이 0.95 미만이면 사람 교정 분량을 늘린다 |
| 2. 렌더 데이터 학습 | 2~3주차 | A층으로 S·M·L 학습, 절제를 개발셋에서 비교. 크기와 문턱을 개발셋에서 고정 |
| **G2** | 3주차 끝 | 개발셋에서 현행(0.629) 대비 CI 하한이 0을 넘지 못하면 **중단**. 중단하면 원인(데이터·용량·타이밍)을 기록한다 |
| 3. 실제 DI 데이터 추가 | 4~5주차 | A+B층으로 이어서 학습, B층 효과를 절제로 확인. B층이 50곡 미만이면 C층(의사 라벨)을 시험 |
| **G3** | 5주차 끝 | 개발셋으로 최종 후보 하나를 고정하고 이후 바꾸지 않는다. 판정 규칙을 바꾼 적이 있으면 날짜와 이유를 확인한다 |
| 4. 최종 판정과 통합 | 6주차 | T1~T4를 한 번씩 채점, `eval/BEST_RESULTS.md`에 기록. 통과하면 전체 곡 베이스 opt-in 경로 + ONNX 사이드카 |

### 위험

| 위험 | 신호 | 대응 |
| --- | --- | --- |

## 오버나이트 작업 규칙 (이 계획에 적용)

- `../reports/Trackform 앞으로의 방향.md`의 원칙 1~7을 따른다. 특히 테스트셋(T1~T4)으로 학습·튜닝하지 않고, 홀드아웃 판정은 후보마다 1회만 한다.
- T1 교정은 사람이 해야 한다. 오버나이트 작업은 초안 생성·정렬 확인·매니페스트까지만 하고, 교정되지 않은 라벨로 T1을 채점하지 않는다.
- 피아노 경로 코드와 프론트엔드는 건드리지 않는다. 공용 백엔드(8000)는 재시작하지 않는다.
- 다운로드는 공식 출처에서만, 신청·로그인이 필요한 데이터는 사유를 기록하고 건너뛴다.
